# polari-dev-tools (dt arc): rules, linting, scaffolding for modules AND apps, and bringing a custom module online — PLAN

**Date:** 2026-09-08 · **Status: PLAN (dt-0).** His framing: "enforce some
coding and structuring rules on polari modules, that way we can do linting
and other things when people make Polari Modules from scratch or have them
generated by no-code and then want to go in and manually modify them. The
polari-dev-tools may need to be its own project … work with the polari cli,
for autogenerating new kinds of polari modules and apps from the cli (apps
should have a scaffolding based on its component pages, modules, routing,
etc as well) … someone running a normal polari that has been installed
should be able to use the cli to bring a valid custom coded and/or no-coded
module they made online onto their own polari instance."

## 0. What already exists (the seed of the project, in the framework today)
- The standard: `AI-Notes/designs/STANDARD_POLARI_APP.md` §2 (manifest),
  §7 (one class per file under `objects/`, taxonomy folders, indexes).
- `moduleService/manifests.py` — generate / validate / conform / readme.
- `moduleService/standardize_layout.py` — the migration verbs (plan /
  apply / fold-subpackages / split-objects / import-all).
- `moduleService/scaffold.py` — `pol modules new`, `pol modules add-object`.
- `moduleService/selftest_manifests.py` — the machine-checked contract.
- The dynamic-modules machinery (dyn-1..9): `POST /modules/{m}/admit`,
  `fetch-admit`, the module deb builder, `isle app admit`.

## 1. Why its own project
Rules + linters + scaffolds are used BEFORE a module exists in a Polari
checkout (a downstream developer starts from nothing) and OUTSIDE the
backend (a CLI on a laptop, a Jenkins stage). They must not require
booting the framework, and their release cadence differs. So:
**`polari-dev-tools/`** — a sub-project (later its own repo + submodule,
like polari-cli), pip-installable (`pipx install polari-dev-tools`),
also vendored by the `pol` CLI (`pol dev …`). The framework keeps only
the runtime half (manifest LOADING, admission).

## 2. Rules → a linter (`pol dev lint <module-dir>`) — dt-1
Rule ids, each with a fix hint; `conform` becomes the first rule family:
- **PA-100 layout**: manifest present + valid; postfix concept files;
  `objects/` one class per file (a class outside objects/ or a
  multi-class object file = PA-101 info / PA-102 warning); stray
  subdirectories; `custom/` for the rest.
- **PA-200 objects**: `treeObject` base + `@treeObjectInit`; first field
  `name: str = ''`; typed defaults; the docstring template present (what
  it is / related concepts / how measured or derived) — a bare docstring
  is PA-201 warning; class name == file name.
- **PA-300 seeds**: `SEED_*` rows carry `name`; upsert never insert-by-name;
  `initialData/` files are `module-initial-data/1`.
- **PA-400 pages**: no `api-json-panel`; every table's columns exist on the
  class (the nutrition page selftest's rule, generalised); `pageRoute`
  unique.
- **PA-500 api**: routes under `/api/<id>/`; the constructor imports only
  its own package (the lazy-imports rule); refusals carry evidence + knob.
- **PA-600 selftests**: `<topic>_selftest.py` present; prints `X/Y checks
  passed`; exit code honest.
- **PA-700 hygiene**: no secrets, no NC-licensed vendored data without a
  LICENSE note, module-name prefixes only in custom/.
Output: text + JSON (Jenkins consumes it); `--fix` for the mechanical
ones (postfix renames, split-objects, manifest refresh).

## 3. Scaffolding modules AND apps — dt-2
- Modules: `pol dev new module <id>` = today's scaffold, moved here, plus
  `add-object`, `add-page`, `add-api`, `add-seed`, each wiring the index
  and the manifest.
- **Apps** (`PolariAppDefinition`): `pol dev new app <id> --modules a,b
  --pages p1,p2` scaffolds the app row (modules_json, pages_json,
  nav_json with routing groups, personas), a page per route through
  `module_pages_seed` (tables only), the nav group, and the app's own
  selftest (every page resolves, every module in the manifest set).
  Apps generated by the no-code side land in the same shape, so hand
  edits and generated code are the same thing.
- Hardware apps: `--kind hardware-app` adds the catalog row + domain
  template stubs (HARDWARE_APPS_PLAN §0).

## 4. Bringing a custom module online on an installed Polari — dt-3
`pol dev admit <module-dir> [--instance <name>]` on a normal install:
1. `lint` must pass the error-level rules (warnings shown);
2. build the module deb locally (`app_deb_builder`, online/offline
   flavor by the install mode file);
3. stage it (`dpkg -i` / `isle app admit` on an isle; `POST
   /modules/seed` + `POST /modules/{m}/admit` on a bare Polari) —
   the dyn-2/dyn-4 path that already exists;
4. the manifest is registered as a `kind: self` module (the registry's
   third kind, unused until now) so it shows in the store and the
   topology like any other, and `pol modules conform` keeps watching it.
No-coded modules take the same road: the no-code side writes the
scaffold's shape (dt-2), so `admit` never has to know who wrote it.
