## 0. Purpose and the two rules

His ask (2026-10-01): *"record all of those and make columns that track the capabilities that are going to be
important for Polari down the road … account for resources we can rely on to develop out our own capabilities."*
This is that record. `board-programming` brd-0 turns §1 into `BoardDefinition` seed rows, §1a (added 2026-10-01)
into `AdapterDefinition` rows, §2 into `OpenCore` rows, and §3 into a `DevelopmentResource` row kind; §4 is a
configured display over them, not hand-written JSON.

**RULE 1 (his, refined 2026-10-01):** a board/module is admitted as a board-arc device if it is **reachable from the
Polari host over USB, directly or through a known USB adapter** — a USB-UART bridge, USB SWD/JTAG probe, USB ISP
dongle, USB mass-storage bridge, or USB I2C/SPI bridge, registered in §1a. His ruling today: *"adapters are
allowed — a board counts as USB-programmable if the Polari HOST side is USB or USB-C, directly OR through a USB
adapter/programmer."* A row that previously read "excluded — JTAG/SWIO/UART-only, no USB" is re-admitted as a
candidate the moment a §1a adapter closes that gap (e.g. SWIO via WCH-LinkE, a UART ROM bootloader via a USB-UART
bridge); only a route with **no USB anywhere in the chain** — or one whose USB path is still undocumented — stays
excluded. Excluded rows are kept with the reason, never deleted.
**RULE 2 (his):** microcontroller and hardware work is written in C, Verilog, or SystemVerilog only — no C++
(no Arduino core/sketches), no MicroPython/Rust on MCUs, no VHDL on hardware. Host-side code (Java bridge/apps,
Python/TypeScript web stack) is a different layer and unaffected (`language-layering`).

**Column definitions (one line each, §1):** `id` = kebab-case row key. `class` = device category. `status` = his
decision state. `chip` = the SoC/MCU/FPGA part. `ISA/arch` = instruction set or fabric family. `MMU` = whether the
core can run a full OS with virtual memory. `flash/SRAM` = non-volatile code store / working RAM. `USB programming`
= the exact USB-only flash route, or why it fails RULE 1. `core RTL open` = is the compute core's register-transfer
source available to us, not just the chip. `board design open` = are schematics/PCB files published. `silicon
origin` = who fabs/designs the chip, and where. `board origin` = who designs/sells the board, and where. `tiers
proven` = which software tier (bare C / FreeRTOS / Zephyr / Linux) has actually been run on it by us or a cited
source. `radios` = on-board wireless relevant to Reticulum/ham/HaLow capability. `power/BMS relevance` = is it
solar/battery-management class hardware. `twin` = the no-hardware simulation stand-in. `Polari role` = how the brd
arc or hardware architecture uses it. `relied-on resources` = the SDK/firmware/driver/toolchain projects the row
leans on (cross-refs §3). `cost measured` = has the engines-ladder cost rule (image/RSS/CPU-s/disk/time) run on its
toolchain yet. `adapter needed` (added 2026-10-01, RULE 1 refinement) = `none (native USB)` when the board has its
own USB/USB-C device port, an id from §1a when a USB adapter/programmer closes the gap, or `?` when the USB path is
still undocumented. `notes/unverified` = caveats, citations, open questions.

## 5. What is unverified, and how this becomes rows

**Unverified (collected).** Every `?` cell above is a gap, not a guess. The largest clusters: flash/SRAM sizes for
most non-UNO MCU boards (never pulled from a datasheet in the source notes); board-design-openness and HQ/country
for several radio-modules and VR/server/phone orgs; exact USB-flash mechanisms for Milk-V Duo, K210 Maix Bit,
Newracom/Morse Micro boards, Mobilinkd TNC4, and (tr)uSDX; licence terms for ~15 of the organisations in §3 beyond
what the source notes stated outright. Carried over from the plan without re-verification: his UNO's exact by-id
path, the Optiboot DTR-reset window length, whether Libero's EULA permits containerised use, the BeagleV-Fire
gateware repo's licence (git.beagleboard.org fetch was blocked for the opus research pass), NaxRiscv's licence, and
Mulan PSL v2's GPLv3 compatibility for XiangShan. New this session (first pass, pre-adapter-ruling): Precursor's
main-SoC core (only the iCE40 UP5K EC is identified in the source note), and whether Milk-V Duo exposes any USB
recovery/flash mode at all (resolved below — it does, via RNDIS/NCM).

**New unverified, 2026-10-01 (§1a adapters pass).** K210 Maix Bit's and (tr)uSDX's onboard USB-bridge chips are
assumed-native but not confirmed (both marked `?` in `adapter needed`); Newracom/Morse Micro HAT/dongle boards'
exact USB-bridge chip is still unconfirmed; `digirig-mobile`'s hardware/firmware openness (both `?` — no
open-hardware claim found, and no separate Digirig-authored firmware identified beyond the CP2102/CM108 silicon);
Digirig Mobile's current kit price (reseller-quoted, not independently confirmed); Black Magic Probe's exact
current-generation hardware part and board-openness extent beyond "legacy schematics public" (1BitSquared has not
republished current schematics per the sources fetched); ST-LINK/V3 pricing across all variants; Bus Pirate 5's
exact firmware licence (open-source per the project, specific licence text not re-read this session); Tigard and
Glasgow Interface Explorer board-level BOM sourcing/manufacturing country (design is open and published; the
assembled-board origin beyond the named maintainer/distributor was not traced further); whether CH32V003 flash/SRAM
is 16 KB/2 KB across all variants of the part (nominal figure, not pulled from the datasheet's full table this
session); and the exact onboard USB-UART bridge chip for generic unbranded CP2102/CH340 modules (genuinely varies
by seller — "CP2102/CH340-class" is as specific as a generic module gets without a part in hand).

**How it becomes rows (brd-0, per the plan's §2 object model).** Every non-excluded row of §1 seeds a
`BoardDefinition` (its `usb_ids`, `programmer`, `transport`, `flash_kb`/`ram_kb`, `twin`, `usb_rule_ok`, and
`adapter_id` (nullable FK into the §1a rows, added 2026-10-01) come straight from this table's columns); excluded
rows seed `BoardDefinition`s too, with `usb_rule_ok = false` and the reason, so `brd_selftest` can assert the rule
rather than silently omitting them. Every row of §1a seeds an `AdapterDefinition` row (kind, chip, usb connector,
targets, engine, hardware/firmware openness, origin, price class) that a `BoardDefinition` references through
`adapter_id` instead of re-stating adapter facts per board. Every row of §2 seeds an
`OpenCore` row (core, ISA, MMU, size, licence, USB route, tier pick, editable flag) that a `BoardDefinition`
can reference when its core is one of these. Every row of §3 seeds a `DevelopmentResource` row (the new kind his ask
calls for) with fields `what/country/provides/licence/feeds/how/risk/status`. §4, the capability matrix, is never
hand-maintained JSON (per `no-raw-json-on-screens`) — it is a configured Table/Graph display joining
`BoardDefinition` × `DevelopmentResource` by a shared capability tag, so the matrix updates itself as rows are added
instead of drifting from this document.
