# UI review: Electronics frontend (release 87), Hardware & Firmware app — 2026-11-15

Done in Chrome (claude-in-chrome) against `https://electronics.isle` → backend `api.polari-pol.isle` (release-87 image).
What is live: hal-0 (`/api/hal/isotopes`). NOT live: hal-iso (`dev-hal-3b` 433826c2, `/api/hal/isotopes/<key>/needs`) and
the hal-ui phases ui-0..ui-3; they need the next backend/frontend release (88).

Pages walked: landing, Apps menu, Hardware & Firmware home, Isotope variants, Sim bench (start a session), Uno core demo
readiness ("Is it ready?"), Uno core demo (the light toggle), Chips and levels.

## Bugs (ranked)

1. **Sim bench cannot start a twin (blocking the whole simulation path from the UI).** `POST /api/board/twins {config}` →
   502: "the session started on the worker but its control port could not be reached from here (board-engines.isle:9833
   unreachable: Connection refused); it was stopped. Is the port range 9832-9863 published …". Root cause (econ, read-only on
   econ): a design gap, not config. board-engines.isle resolves to econ's isle agent, whose nginx
   serves only 80/443; the worker container EXPOSEs 9830-9863 but the isle deploy publishes no host ports (by design), and
   `twin_sessions.py:147` opens plain TCP to `<worker host>:<ctl_port>` — the dev-compose assumption. **User decision:**
   (A) agent **stream** proxy: release.json declares TCP `streams`, the agent writes an nginx `stream {}` with `listen <p>
   ssl` using the app's leaf cert; Hub/TcpDevicePort verify TLS against the isle root (econ's recommendation, generic);
   (B) tunnel ctl/tcp over the worker's HTTPS API (WebSocket per session; more latency on the USART path);
   (C) plain host ports + a separate name (breaks "everything is certified TLS through the agent"; advised against).
2. **The refusal words are rendered where nobody sees them.** `class-rows-table` prints an action's failure in
   `<p class="message bad" role="status">` AFTER the table, INSIDE the capped scroll box (`.class-rows-table.scrolls`); with
   the ~40-row firmware list the message sits ~8300 px down. The panel text promises "the refusal says so in words"; in
   practice the button looks dead. Fix: message above the table, or sticky at the box bottom, or a toast. (pol frontend.)
3. **NG0100 ExpressionChangedAfterItHasBeenCheckedError in `DisplayRendererComponent`** on every display page
   (previous '0', current '1803' — a measured width bound in the template during the same change-detection pass). Console
   error on each navigation; fix by measuring in `ngAfterViewInit` + `detectChanges`, or a signal/async binding.
4. **Isotope variants, ESP32-C3 table, misleading data.** Its heading says "its pin routing is not modelled, so many are
   undetermined", yet every C3 row reads `ok on esp32-c3: every pin kind, block, part and the runtime tier are available`,
   and C3 rows carry UNO text and evidence: "External interrupt (INT0 / INT1)", "only two pins can do it on the UNO",
   `status compiles … shipped build of uno-button-clock … sizes measured in uno-button-clock`. The status is supposed to be
   read off what exists; UNO builds must not be credited to C3 variants. (board/cmod backend.)
5. **The light toggle lies by omission.** On `/display/uno-core-demo`, "Turn the light on / off" flipped `led_on` to
   `true` with `toggles 0, source —, status idle`, while the readiness page says the bridge is **missing**. The page claims
   "the board always telling this screen what the light is doing"; with no bridge/twin the row should say the command is
   stored and nothing will follow (or the button should be disabled with the reason). Also no HTTP request appeared for the
   action (it travels another way); the user gets no confirmation at all.
6. `hardwareapps` shows a `power_off` chip on the app home with no words; `/api/board/engines/status` 404s (the page polls
   it); `/api/terms/active?app=app-hardware` 404s on every page; `[roleplay] could not read observe/roles` warning on
   every page. Low severity, all noise that hides real failures.
7. Sim bench: "Loading the layout…" stays on screen above a picture that has already rendered.

## Intuitiveness feedback (the interface is dense; these would help most)

- **Every page opens with a wall of prose, then repeats it.** Sim bench shows the same 120-word paragraph twice (page intro
  + panel header). Make the intro one sentence + a "How this works" disclosure; put the long text behind it.
- **Tables need a filter/grouping before a reader can act.** Isotope variants is 6 jobs × 7 routes × 2 boards with 17
  columns; the firmware list mixes 14 real configs with 20 `SCENARIO ONLY` rows. Add: board selector, "hide blocked",
  "hide scenario-only", and collapse cost columns into one "cost" cell with a hover.
- **"page" chips are not obviously clickable** (the whole row is the click target, the chip is a label). Make the row a
  link with hover, or make the chip a real button.
- **State words are internal.** `declared / template-exists / compiles / proven-on-twin / proven-on-hardware` and
  `planned / incomplete / missing` are good, but each table should have a legend line, and the composition row's verdict
  should be the first thing on the readiness page, not the last.
- **The home page should say what to do next.** The Hardware & Firmware home is a catalogue; put a "Start here" strip:
  1 pick a board → 2 start a twin → 3 press the button → 4 install for real, each linking to its page, each showing its
  readiness (the readiness door already computes this).
- **Developer breadcrumbs in user text**: CLI invocations and door paths (`python3 -m cmod.custom.isotope_variants …`,
  `GET /api/atom-jobs`) in page intros belong in a "for developers" footer.
- **Feedback after any button**: a visible result (toast or inline next to the button) for every action, success or
  refusal, with the words the backend already produces.

## What worked

Navigation, the app grouping and top bar, the Sim bench picture (board + breadboard, net check "OK: 4 nets equal"),
the readiness table's honesty about the missing bridge, Chips and levels (clear levels/sources), consistent light/dark
tokens. The backend's refusal words are uniformly good; the frontend just has to show them.
