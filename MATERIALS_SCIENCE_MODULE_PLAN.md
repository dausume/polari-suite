# Materials Science Module — Plan

**Status: DRAFT for Dustin's review (2026-07-06, written by Claude per the pre-work directive).
Nothing below is started without confirmation except where marked already-done.**

The Materials Science Module is the **2nd multi-scale-simulation test case** (after
pendulum-in-wind). It will get computationally heavy, so it must exercise ALL the
compute/distribution capabilities — the infra tracks below are prerequisites, not side
quests. Standing principles apply throughout: knobs + evidence-bearing suggestions (never
auto-apply), object coherence (every capability lives on an object in the tree and is
configurable at that object), small files split by concern, branch per confirmed phase.

## Infrastructure tracks (roughly in order)

### Track 1 — Distribute load over the 3 computers

Machines: **this box** (192.168.0.210 — staging stack + twin B), **isle-core**
(detts@192.168.0.24), **lightweight** (dausume@192.168.0.66).

Proven ladder to build on (DISTRIBUTED_COMPUTE_PLAN.md): Dask parallel search (6×),
twin instances, cross-instance Dask (5/5 worker split), PeerAgreement admission +
module install over the peer link.

Everything proven so far rides docker-internal networks (`polari-link` on ONE host).
Going multi-machine needs exactly what the twin lab deliberately abstracted away:

1. **Core-and-remote compose variants** (Dustin's added directive): compose files where
   peer/service addresses are **manually entered IP:port env vars** instead of docker
   DNS names. Concretely:
   - `docker-compose.remote-worker.yml` — a Dask worker (+ optionally a peer backend)
     that connects OUT to `POLARI_CORE_HOST:PORT` (scheduler `tcp://IP:8786`, API
     `http://IP:8081`), publishing nothing locally except its own worker port.
   - Core side: publish the scheduler + peer API ports on the host interface (staging
     compose today only exposes them on internal networks).
   - Knob shape: a small `.env.remote` (CORE_IP, SCHEDULER_PORT, PEER_API_URL,
     POLARI_PEER_TOKEN) generated by a `remote-setup.sh` sibling of staging-setup.sh.
   - Trust: reuse the PeerAgreement admission flow — a remote node presents the same
     peer token/handshake it does on the twin, just over LAN.
2. **Deploy order**: lightweight first (reachable now, weakest hardware = honest test
   of the resource-aware machinery), isle-core when it's back up.
3. **Acceptance**: a stage-search batch run on this box splits attempts across workers
   on ≥2 physical machines; `dask-status` shows the remote worker; kill the remote
   worker mid-run and the run completes (Dask reschedules).

### Track 2 — Modules as PROJECTS (selective fetch)

Goal: NOT all modules downloaded at start. Some modules become their own repos/projects,
pulled into the workspace by configuration and by choosing to download them.

Foundation that already exists (`polari-framework/polariPeers/`): PolariModule registry,
bundle export/install (proven A→twin-B live), `source_kind` already enumerates
`'github'|'git'|'file'|'peer'`. The gap is **config-driven selective fetch of module
projects into the workspace**:

1. `ModuleSourceConfig` (new persisted class, object-coherent: rows in the object tree,
   editable via the auto-CRUDE API): name, source_kind, locator (repo URL / peer name /
   path), ref (branch/tag), `autoFetch` knob (default off), install scope.
2. Fetch engine in `polariPeers/module_loader.py` (or a sibling `module_fetcher.py` —
   keep files small): given a ModuleSourceConfig, materialize the module folder under
   `modules/` (git clone/pull for github|git, bundle install for peer, copy for file),
   then run the existing install path.
3. Startup behavior: modules NOT configured are simply absent — boot must tolerate
   missing module folders (audit CLASS_LOAD_ORDER / module discovery for hard imports).
4. Suggestion (per knobs-and-suggestions): when a definition references a class from an
   uninstalled module, surface an evidence-bearing suggestion pointing at the
   ModuleSourceConfig knob — never auto-fetch.
5. First real customer: the Materials Science Module itself ships as a fetchable module
   project.

### Track 3 — DB layer switchability (sqlite ↔ mariadb / KeyDB)

Current: `polariDBmanagement/managedDB.py` is sqlite-only (plus the 2026-07 boot-time
`_syncTableColumns` schema sync). MariaDB already runs in-stack (prf-mariadb, Keycloak's
store). KeyDB verified drop-in-compatible with the psc redis approach (see §0).

1. **Interface extraction first**: split managedDB into a thin `DBAdapter` interface
   (connect, ensure-table, sync-columns, CRUD, query) + `SqliteAdapter` holding today's
   behavior. Selftests run against the interface. (file-size-decomposition: new files,
   not a bigger managedDB.py.)
2. `MariaDBAdapter` — same table-per-class model; reuse prf-mariadb with a second
   database + dedicated user. Schema sync must translate (SQLite `ALTER TABLE ADD
   COLUMN` ≈ MariaDB, but type mapping differs — reuse the polyTyping type map).
3. `KeyDBAdapter` — object/cache store (redis protocol via redis-py). Natural first
   uses: Dask result caching, run-series hot storage, cross-instance shared state —
   NOT the system-of-record. Compose service `prf-keydb` modeled on psc-redis
   (rebased Dockerfile per §0).
4. Knob: `DATABASE_TYPE` env already exists (compose sets `sqlite`) — extend to
   `mariadb`, plus a separate `CACHE_BACKEND=keydb|none`. Per-class storage-backend
   overrides can come later; don't over-build now.
5. Acceptance: full backend selftest suite green under both DATABASE_TYPE values;
   a fresh boot seeds identically on mariadb.

## Module design tracks (after/alongside infra)

### Track A — Ground the basis in the existing module (review DONE 2026-07-06)

Full code review of `modules/polariMaterialsScienceModule/` (116 treeObject classes,
~15,200 LOC) completed. What's there and what it means for the basis:

**Structure that survives (good bones):**
- Property trees with a 3-level abstraction axis (L1 abstract concept → L2 derived
  value → L3 raw measurement) and ~21 real single-property `calculate_*` reducers
  (Krebs viscosity from Stormer measurements, Owens-Wendt surface tension, engineering
  stress/strain, etc.).
- The 5-level resolution taxonomy (0 Experimental → 1 Continuum/FEM → 2 Mesoscale/CGMD
  → 3 Atomistic/MD → 4 Quantum/DFT) with concrete per-level definition classes
  (ConsistentFiniteElementMaterial, MolecularDynamicsMaterial, DensityFunctionalMaterial…).
- The additive/formulation schema: MaterialAdditive + PropertyEffect
  (`effectPerWeightPercent`, `normalizedEffectStrength`) + AdditiveCompatibility +
  Compatibilizer + Formulation/FormulationComponent/FormulationIntent +
  TargetMaterialProfile/PropertyTarget (optimum + hard min/max + weight).
- DataProvenance/DataSource credibility subsystem (`provenanceId` on nearly everything).
- **Seed data directly usable for Track C**: 28 raw materials (beeswax, carnauba, soy,
  stearin, rosins/oleoresins, clays/fillers, soy lecithin as compatibilizer), 62
  PropertyEffect rows, 8 target profiles incl. "Machinable Wax (Print2Cast)" and
  "Minimum Viable Wax Filament" with 88 PropertyTarget rows.

**Core gaps the basis must fix:**
1. **Three disjoint material roots, unlinked**: `Material` (anchor of
   property/resolution/purpose trees — zero seed rows), `RawMaterial` (anchor of the
   seeded formulation world), `ReferenceMaterial` (PLA/ABS/… literature classes). The
   MaterialsScienceMaterial basis must unify or explicitly bridge these.
2. **Multi-scale is labels, not weaving**: resolution rows share only a `materialId`
   string; nothing links a level-1 FEM definition to the level-3 MD definition it came
   from; `RulesOfMixturesExperimentalMaterial` documents Voigt/Reuss/Halpin-Tsai but
   contains NO math (pure data holder).
3. **No formulation math anywhere**: the schema anticipates
   Σ(weightPercent × effectPerWeightPercent) blending and PropertyTarget scoring, but
   it was never implemented — Track C builds exactly this.
4. **Module ↔ simulation bridge nonexistent**: the stage/gate machinery
   (multi_scale_stages.py, multi_scale_search.py, MaterialCondensationState) never
   imports the module; module = static data, simulations = executable weaving. This is
   the central integration Track B addresses.
5. **Convention drift**: old module is camelCase / manager-FIRST / @treeObjectInit / no
   type hints / GPL headers; the new `materialsScience/` package
   (ChemicalElementDefinition, 118 elements) is snake_case / manager-LAST / typed /
   `default_initial_field_values` + `field_save_policy`. New basis code follows the NEW
   conventions; old classes get bridged or ported per phase, not wholesale-rewritten.
   (Watch: two overlapping "level" systems — resolutionLevel 0-4 vs abstractionLevel
   1-3; keep names distinct in the basis.)
6. Minor debt: seed loader lists formulations.json/formulationComponents.json/
   formulationIntents.json that don't exist and swallows failures silently; sourcing
   subclasses hand-copy ~20-field parent signatures (brittle); `minimumOrderOrderUnit`
   typo; base MaterialProperty lacks `materialId`.

Output of Track A (mostly satisfied by this review): the decisions above, confirmed by
Dustin, become the written basis spec that Tracks B/C build on.

### Track B — Piecemeal-first multi-scale foundation

Lay the foundation for going ALL THE WAY (full multi-scale material definition) but
build one piece at a time. **Piecemeal definitions are first-class**: not every material
can be defined at every scale, and an honest partial model with explicit gates beats a
fake complete one (same philosophy as the condensation space).

- A material carries N scale-level definitions (0..5), each independently present or
  absent; presence is queryable ("what can this material prove at level 3?").
- Gates: a simulation stage declares which scale-levels it needs; missing levels produce
  explainable refusals + suggestions (which knob/definition to add), never silent
  fallbacks.
- Cross-scale links are explicit objects (e.g. "level-2 crystal structure → level-4
  bulk modulus via <relation>"), so provenance of a derived property is inspectable.

### Track C — Rules-of-mixtures wax composites (target-seeking search)

Leverage a rules-of-mixtures library and build the capability to design **wax
composites** by seeking targets from pre-existing materials OR manually entered property
ranges/values.

- Engine: this is a target-seeking SEARCH over composite formulations — the
  multi-solution stage-search machinery (`continueAfterWinner`/`stopPolicy`,
  parallel/dask backends in `simulations/multi_scale_search.py`) is the natural fit,
  and the computational-heaviness driver for Tracks 1–3.
- Inputs: base material + candidate additives (existing formulation/ +
  materialAdditives/ subpackages), target spec = property ranges or exact values
  (manually entered rows — object-coherent, editable in the UI).
- Rules of mixtures: start with the classical bounds (Voigt/Reuss, Halpin-Tsai as a
  knob) as no-code matrix equations where feasible, so the math is visible in the
  editor rather than buried in Python. The existing schema already anticipates the
  linear blend model (Σ weightPercent × effectPerWeightPercent vs PropertyTarget
  hard-min/max + weights) — implement that first as the level-0 rule, classical bounds
  as the next rung. `RulesOfMixturesExperimentalMaterial` (data-only today) becomes the
  home of the computed result.
- Seeds to build on: the module ships 28 raw materials (waxes + fillers + soy-lecithin
  compatibilizer), 62 PropertyEffect rows, and the "Minimum Viable Wax Filament" /
  "Machinable Wax (Print2Cast)" target profiles with 88 PropertyTarget rows — the wax
  composite test case is already half-seeded.
- Surface: reuse the solid-materials-selection machinery — selection spaces for picking
  base/additives (periodic table + material selector already live), condensation-style
  gate flow for "does this formulation meet the target", explainer panels for
  tried-formulation maps.
